# Solid State Physics — Assignment 1

## What this repo is
Coursework repo for SSP Assignment-1 (6 questions, 10 marks each; each group submits
**two**). Our assigned questions live in their own folders:

- [question_3/](question_3/) — Interactive Python interface for **phonon dispersion in a 1D
  multi-atomic lattice**. *Primary focus right now.*
- [question_5/](question_5/) — Interactive Python interface for **Fermi–Dirac statistics in a
  semiconductor crystal**. Not started.

Each question folder carries its own `SCOPE.md` (what must be delivered, fixed physics and
conventions) and `PROGRESS.md` (running log of what is done / in flight / blocked). Read both
before touching code in a folder, and update `PROGRESS.md` at the end of a work session.

## Deliverable rules that come from the assignment PDF
These are grading criteria, not suggestions:

- Complete Python source as **`.py` files**, with comments marking each major step.
- **Screenshots of the interactive interface** must exist for the report.
- Results for **several different input parameter sets**, each interpreted in words.
- Every plot labelled: axis labels with units, legend, title.
- A derivation / theoretical background section, not just code.
- References at the end (textbooks, docs, tutorials).
- Named contributors with roll numbers, and who did which part.

## Layout
One venv at the root, shared. Each question folder is self-contained and runnable on its own;
the only shared code is `common/style.py`.

```
common/style.py      matplotlib defaults, so both reports' figures match
question_3/          phonon.py  app.py  make_figures.py  test_phonon.py  figures/  report/
question_5/          same shape, different physics
```

**Keep `common/` small.** Q3 and Q5 share a plot style and a set of habits, not logic. A helper
that wraps two call sites which don't quite match costs more than it saves. If a third use shows
up, promote it then.

What actually carries over between the two questions is convention: the core/UI/figures/test
split, validating against a closed-form limit before trusting the general code, and sweeps
driven from `make_figures.py`. Written down here, not imported.

## Code style
Simple and direct. This is coursework physics, not a library.

- Plain functions over classes. No config objects, no framework.
- numpy arrays in, numpy arrays out. The core never imports streamlit or matplotlib.
- Short names where the physics names them (`q`, `omega`, `m`, `K`), spelled out otherwise.
- No premature generality — write the case we need.

**Comments.** The PDF wants "comments marking each major step", so use short `# ---- step ----`
section markers to satisfy that, and otherwise comment only where the code alone misleads:
a sign convention, a non-obvious index, a unit choice, a formula worth naming. One line each.

No docstring essays, no comment restating the line below it, no explaining what numpy does.
If a block needs a paragraph to justify it, that paragraph belongs in `report/`, not the source.

```python
# ---- dynamical matrix ----
D[0, -1] = -K * np.exp(-1j * q * a) / np.sqrt(m[0] * m[-1])   # inter-cell bond, carries all q-dependence
```

## Working conventions
- Python toolchain: `uv venv --python 3.12` inside the question folder, then
  `uv pip install numpy scipy matplotlib streamlit`. System `python3` is 3.8 with nothing in it.
- Physics core and UI stay in **separate modules**. The core takes numbers in and returns
  numbers out, so it can be tested without launching a GUI.
- Every physics module gets a numerical check against a closed-form limit before it is used in
  the report. Do not report a number that no check covers.
- Figures are generated by a script into `figures/`, never saved by hand out of a GUI, so they
  regenerate reproducibly.
- `RESEARCHER.md` is the user's private research-method notes. It is gitignored; do not commit
  it, quote it into deliverables, or treat it as assignment content.

## Writing style — applies to everything
`WRITING.md` is the style guide for all prose in this repo: report sections, comments, commit
messages, and replies in chat. Follow it by default; it does not need to be invoked. Two things
it insists on that are easy to drop:

- **Length tracks content, not topic.** One line if one line does the job. Don't expand a point
  to three sentences because the section looks thin (§12).
- **No boilerplate scaffolding.** No generic openers, no ceremonial transitions, no closing
  paragraph that re-says the section (§2, §6).

Like `RESEARCHER.md`, it is gitignored — it shapes the writing, it is not part of the submission.

## Tone for written deliverables
The report is read by a course instructor. Derivations are explicit and assumptions stated, and
every figure gets interpreted — a plot with no sentence explaining it scores nothing. That is a
reason to cover each figure, not a licence to pad: one accurate sentence about a plot beats a
paragraph circling it.
